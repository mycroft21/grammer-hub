# 코딩 에이전트 프롬프트 벤치마크 (2026-09-22)

> 질문: 사람이 아니라 **Claude Code·Codex 같은 코딩 에이전트**에게 줄 "스타터 프롬프트"는 어떻게 써야 하는가. 공개된 지침이 무엇을 권하고, 우리 스튜디오의 슬롯·질문 정책·프로필은 거기서 무엇을 가져왔는가.
> 방법: 소스군 5개를 병렬로 조사(1차 출처만: 벤더 공식 문서·엔지니어링 블로그·논문·제품 도움말) → 규칙마다 원문 인용 → 종합 → 반대 검토. 조사 에이전트는 Sonnet, 종합·검토는 Opus.
> 한계: 이 세션의 네트워크 프록시가 `www.anthropic.com`, `developers.openai.com`, `docs.github.com`, `cursor.com`, `docs.devin.ai` 등을 막아 일부는 GitHub 원본 저장소·미러·검색 요약으로만 확인했다. 부록 A에 `직접 확인 / 간접`을 표시했고, 간접 인용은 정확도가 낮다.
> 근거 등급은 [docs/10](10-prompt-engineering-references.md)과 같다: **[1차]** 공식 문서·논문이 직접 권고 / **[경험칙]** 벤더 템플릿·커뮤니티 관행 / **[우리 판단]** 출처 없음.

## 0. 한 줄 결론

두 벤더(Anthropic, OpenAI)와 Copilot·Devin·Jules의 지침은 놀랄 만큼 같은 말을 한다: **결과물과 "끝난 상태"를 관찰 가능하게 쓰고, 에이전트가 스스로 돌릴 수 있는 검증을 주고, 범위를 잠그고, 저장소에서 알 수 있는 것은 적지 말고 찾게 하고, 저장소 상식은 프롬프트가 아니라 저장소 옆의 파일(CLAUDE.md / AGENTS.md)에 두라.** 스튜디오 v0.5는 이 다섯을 코드로 강제하도록 바꿨다(§5).

## 3. 저장소 지식은 어디에 두나 → 작업 공간 프로필

모든 벤더가 "매 프롬프트에 반복하는 것은 저장소 옆 파일로 올려라"고 한다(Claude Code: promote a fact when re-explained twice; Codex: if you keep reusing the same prompt, make it AGENTS.md or a skill; Cursor: promote repeated chat prompts into rules). 그 파일에 들어갈 것도 일치한다: **빌드·테스트 명령, 비표준 관례, 함정, 저장소 구조의 비자명한 부분**. 넣지 말 것: 코드에서 유추되는 것, 파일별 설명, 일반 상식.

우리 도구는 저장소 **밖**(티켓 → 프롬프트)에서 돌기 때문에 CLAUDE.md를 읽을 수 없다. 그래서 같은 내용을 `studio.workspace.json`으로 받는다(docs/05 §A-3″). 필드 선택의 근거:

| 필드 | 근거 | 쓰이는 곳 |
|---|---|---|
| `repos[].name/what/stack` | Copilot custom-instructions("project overview, tech stack"), AGENTS.md 관례 | 작업 공간 블록, 저장소 질문 선택지 |
| `repos[].aliases` | [우리 판단] — 세 실사용 티켓 모두 병목이 "어느 레포인가"였고, 티켓은 `[partner]` 같은 태그로만 가리킴 | **코드가** 제목·라벨·컴포넌트에서 확정 → where 질문 소거 |
| `repos[].verify` | R2. Codex("if test commands are listed in AGENTS.md the agent will run them"), Copilot("make sure the agent knows how to build, test and validate — the biggest lever") | 완료 조건·검증 재료 |
| `repos[].entry/notes` | Claude Code memory(gotchas, non-default conventions), Amp AGENT.md(Architecture & Structure) | 시작점·맥락·규칙 재료 |
| `conventions` (≤5) | Claude Code(CLAUDE.md 짧게; emphasize at most one line), Cursor(start minimal, add after a repeated mistake) | hard_rules 후보(모델이 관련된 것만) |
| `glossary` | Codex 태스크 문서 지침(define every non-ordinary term), Claude Code(one consistent term per concept) | 텍스트에 나온 용어만 삽입 |
| `projects` | [우리 판단] — Jira 프로젝트 키(ES=보안 점검)가 분류 힌트 | 분류 프롬프트 |

프로필은 "무엇을 넣지 말 것"도 따른다: 디렉터리 트리·의존성 목록·아키텍처 개요는 받지 않는다(에이전트가 저장소에서 읽는다).

## 4. 질문 정책 — 무엇을 묻고 무엇을 가정하고 무엇을 넘기나

벤더 지침과 연구가 가리키는 기준은 세 갈래다.

1. **저장소를 읽어 알 수 있는 것은 묻지 않는다.** Claude Code: "direct Claude to the source that can answer instead of asking the question bare"; Copilot 온보딩 프롬프트: "trust the instructions and only perform a search if incomplete"; Codex: 코드값·구현 위치는 에이전트가 찾는다. → 장부 상태 `agent_can_find` = 프롬프트의 "확인할 것"으로 이동.
2. **사람만 아는 것 중 결과물을 바꾸는 것만 묻는다.** ClarifyGPT 계열의 기준은 "그럴듯한 해석들이 서로 다른 출력을 낳을 때"(부록 B·질문 시점 항 참고), Claude Code는 "가정이 결과를 크게 바꿀 때"; 그 외는 가정을 명시하고 진행. → `ask` 조건 = 어느 저장소 / 업무 규칙·범위 결정 / 첨부에만 있는 핵심 정보, **그리고** 답에 따라 결과물이 달라질 때.
3. **질문은 적게, 한 번에.** Claude Code: "batch your questions"; Codex: "one targeted question"; 우리 목표: 스타터. → 상한 2개, 초과분은 가정으로 내려 검토 화면에서 고치게.

이 셋을 모델 재량에 맡기지 않고 **장부(needs ledger)**로 강제한다(`needs.ts`): 항목마다 `filled / ask / assume / agent_can_find` 중 하나. 항목은 개발 공통 6개(where·deliverable·done·scope·external·policy) + 세부 유형의 mustKnow. 같은 항목이 질문과 가정에 동시에 나올 수 없고, `where`는 프로필이 확정하면 모델 판단을 덮어쓴다. 첫 실사용(EP-1174·ES-476·EP-1161)에서 세 티켓의 질문 행동이 제각각이던 원인이 "판단을 통째로 위임"이었다는 진단에 대한 답이다.

종합(Opus)이 정리한 판정 기준을 그대로 옮긴다. **묻는다**: 티켓에도 저장소에도 없고 기본값도 없으며 두 해석이 서로 다른 작업으로 이어질 때 / 요청자만 내릴 수 있는 결정(어느 동작이 맞는지, 파괴적·사용자 노출 변경 허용 여부, 대상 환경·테넌트) / 파싱 못 하는 첨부에 분류가 달려 있을 때(첨부 내용을 묻는다, 티켓 재진술이 아니라). **가정한다**: 프로필·저장소 관례에 기본값이 있을 때 / 문구와 코드가 한 해석을 더 지지할 때 / 틀려도 되돌리기 싼 것(변수명·로그 레벨·테스트 파일 위치) / 이미 티켓에 있는 것(절대 다시 묻지 않는다). **에이전트에게 넘긴다**: 코드 위치·현재 동작·테스트 프레임워크·헬퍼 존재·호출부 수 / 구현 방식 선택 / 저장소에 있는 재현 스크립트 / "기존 테스트가 있나·깨지나"(직접 돌려야 답이 된다) / 역사·이유("왜 이렇게 됐나" → git log·PR·ADR로).

**한계(정직하게):** "질문 상한 2"와 "우선순위 where > external > policy > deliverable > done > scope"는 [우리 판단]이다. 문헌은 기준을 주지만 개수 상한은 주지 않는다(가장 큰 값은 "최대 5개", 그리고 "더 적고 더 겨냥된 질문"이 성능을 올렸다는 결과). 세부 유형별 기대치: 검토·조사 0개, 버그 수정 0~1, 기능 구현 1~2(범위 경계, 테스트·PR 기대 — 프로필이 답하면 0).

## 6. 종합이 제안했지만 그대로 따르지 않은 것

종합 단계(Opus)의 슬롯별 판정 중 채택하지 않은 것과 이유. 다음 손질 후보이기도 하다.

| 제안 | 우리 결정 | 이유 |
|---|---|---|
| `self_check`를 없애고 완료 조건·보고 형식에 합쳐라(일반적 "다시 확인" 문구가 과잉 검증을 부름) | 슬롯은 유지, **의미만** "끝내기 전에 실행할 구체적 검증(명령·증거)"으로 바꿈. '…했는가?' 되묻기 금지 | 사용자가 "검증 단계"를 한눈에 보고 고칠 자리가 필요하다. 과잉 검증의 원인은 슬롯이 아니라 문구다 |
| `failure_guards`를 `hard_rules`에 합쳐 총 3줄로 | 분리 유지, short는 규칙 3 + 주의 2 | 목적별 씨앗(흔한 실패)은 별도 축으로 관리해야 다듬기 쉽다. 렌더에서는 이미 붙어 있다 |
| `examples` 슬롯 삭제, 대신 "따를 기존 패턴 파일"을 시작점에 | 에이전트 런타임은 null 기본, 슬롯은 chat 런타임용으로 유지 | 채팅 프롬프트에는 예시가 여전히 유효하다(docs/10 §1) |
| `assumptions` 슬롯 신설(0~3줄 "X라고 가정했다. 코드가 다르면 보고에 적어라") | **채택 예정**. 지금은 검토 화면의 가정이 `<assumptions>`로 생성 단계에만 들어가고 프롬프트 본문엔 모델이 맥락에 녹인다 | 가정을 프롬프트에 그대로 노출하면 에이전트가 틀린 가정을 보고에서 바로잡을 수 있다. 다음 버전 |
| `out_of_scope` 한 줄 신설 | 부분 채택: 목적별 범위 유지 문장 + 장부의 `scope` 가정이 그 역할 | 별도 슬롯은 다음 버전에서 `assumptions`와 함께 |
| `clarify_policy`를 에이전트에서 두 값(가정 후 진행 / 특정 행동 전 멈춤)으로 축소 | 세 값 유지, 에이전트용 문구를 "되돌리기 어려운 변경·범위 변경만 멈춤" 기준으로 재작성 | UI·저장 스키마 호환. 문구가 이미 그 기준을 따른다 |
| 규칙 상한 5 → 3 | short는 3, standard 5 유지 | 3은 근거가 "짧을수록 지켜진다"는 방향성이지 숫자가 아니다 |
| 프로필에 `exemplars`(패턴→파일), `agent_files`(CLAUDE.md 존재·요약), `environment`, `human_only`(에이전트에 맡기지 않을 영역: 보안·인증·개인/결제 식별자·장애 대응) | `entry`/`notes`가 exemplars·environment 일부를 담는다. **`human_only`는 채택 가치가 크다** — 다음 버전 | Copilot이 명시적으로 권고하는 항목. ES 같은 보안 티켓을 자동 위임하기 전에 경고하는 용도 |
| 테스트 추가 정책(테스트 없는 저장소에 새 테스트를 넣나)은 저장소별로 프로필에 | 부분 채택: `verify`가 없으면 "기존 테스트가 있으면 통과"로 위임 | OpenAI 자료끼리도 상반(Codex 지시문 "넣지 말라" vs 예시 AGENTS.md "요청 없어도 넣어라"). 프로필 필드로 명시하는 게 맞다 → 다음 버전 |

## 7. 하지 않은 것과 왜

- **파일 앵커의 의무화**: Copilot은 "파일 지정은 앵커일 뿐 필수 아님"이라 하고 Cursor는 에이전트 검색을 선호한다. 우리는 시작점을 필수로 두되(점검), 형태만 강제한다('저장소: 대상').
- **예시 기본 포함**: 코딩 에이전트 프롬프트에서 예시는 "따를 기존 패턴 파일"로 대체된다(R5). 스타일 민감 작업이 아니면 null 유지.
- **훅·권한으로 경계 강제**: Claude Code는 "'don't touch' 한 줄은 권고일 뿐, 반드시 지켜야 하면 훅으로"라 한다. 그건 저장소 쪽 설정이라 이 도구 범위 밖. 문서에만 적는다.
- **프롬프트 안에 검증 명령을 항상 박기**: Codex는 "AGENTS.md에 있으면 프롬프트에 반복하지 말라"고 한다. 우리는 프로필의 `verify`가 있으면 완료 조건에 쓰고, 없으면 "기존 테스트가 있으면 통과"로 위임한다.

## 부록 B. 추출한 규칙 (슬롯별, 원문 인용)

각 줄: 규칙(우리 요약) — “원문” — 출처. 강도: explicit(문서가 권고로 명시) / implied(예시·템플릿에서 드러남) / contested(출처끼리 어긋남).


### B-1. 목표 (14개)

- [explicit] Open the task by stating the observable symptom, the likely location in the repo, and what 'fixed' looks like, rather than naming the bug abstractly. — “Describe the symptom. Provide the symptom, the likely location, and what "fixed" looks like. | "fix the login bug" | "users report that login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it"” — https://code.claude.com/docs/en/best-practices
- [explicit] State the expected behavior, not just the symptom, and name the file or function when you can. — “Name the file or function: "Add a README with setup instructions" or "Fix the failing auth test in `tests/test_auth.py`" is better than "fix tests" * Paste error output if you have it * Describe the expected behavior, not just the symptom” — https://code.claude.com/docs/en/web-quickstart
- [explicit] Give the motivation behind each constraint (the 'why') so the agent can generalize instead of following it literally. — “Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can help Claude better understand your goals and deliver more targeted responses.” — https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices
- [explicit] Be explicit and specific about the desired output; if you want extra thoroughness or 'above and beyond' work, ask for it rather than expecting inference. — “Claude responds well to clear, explicit instructions. Being specific about your desired output can help enhance results. If you want "above and beyond" behavior, explicitly request it rather than relying on the model to infer this from vague prompts.” — https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices
- [explicit] Sanity-check the generated prompt with the 'new colleague' test: if an engineer with no context would be confused, the agent will be too. — “Think of Claude as a brilliant but new employee who lacks context on your norms and workflows. The more precisely you explain what you want, the better the result. Golden rule: Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too.” — https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices
- [explicit] ⚠간접 Default task-prompt skeleton for a large/complex repo: state Goal, Context (files/folders/docs/errors, @-mentioned), Constraints, and 'Done when'. — “A good default is to include four things in your prompt: Goal: What are you trying to change or build? Context: Which files, folders, docs, examples, or errors matter for this task? You can @ mention certain files as context.” — https://developers.openai.com/codex/learn/best-practices
- [explicit] ⚠간접 A minimal good Codex prompt has four ingredients: the behavior wanted, a pointer to the relevant code or repro steps, the constraints that must hold, and how to verify the change. — “A useful Codex prompt names the behavior you want, points to the relevant code or reproduction steps, preserves important constraints, and says how to verify the change.” — https://developers.openai.com/codex/prompting
- [explicit] ⚠간접 Lead with the result, not a step list; only prescribe process when the process itself matters, otherwise leave the agent room to search and adjust. — “Start with the result, not a detailed list of steps. Include the audience or format when those details change what ChatGPT should produce.” — https://developers.openai.com/codex/prompting
- [explicit] ⚠간접 A well-formed task has a clear outcome, a small set of source materials, and an output the requester can review. — “Good tasks have a clear outcome, a few source materials, and an output you can review.” — https://developers.openai.com/codex/prompting
- [explicit] Open with purpose: in a few sentences say why the change matters from the user's perspective, what becomes possible, and how to see it working. — “Purpose and intent come first. Begin by explaining, in a few sentences, why the work matters from a user's perspective: what someone can do after this change that they could not do before, and how to see it working.” — https://cookbook.openai.com/articles/codex_exec_plans
- [explicit] Open the task with a clear statement of the problem to solve or the work required; a well-scoped task is the first predictor of a good result. — “provides better results when assigned clear, well-scoped tasks. An ideal task includes: A clear description of the problem to be solved or the work required.” — https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results
- [explicit] Order the prompt from a broad goal statement to a list of specific requirements. — “Start general, then get specific ... first give Copilot a broad description of the goal or scenario. Then list any specific requirements.” — https://docs.github.com/en/copilot/concepts/prompting/prompt-engineering
- [explicit] ⚠간접 Write the task as a detailed spec you would hand a coworker; specificity is the top rule. — “The most important thing to remember when instructing Devin is to be as specific as possible. Just as you would provide a detailed spec when asking a coworker to code something, you should do the same with Devin.” — https://docs.devin.ai/essential-guidelines/instructing-devin-effectively
- [explicit] Be clear and specific: give enough detail that the model knows exactly what is asked ('sort a list of integers in ascending order using Python', not 'sort array'). — “Be Clear and Specific: Provide enough context and detail so the model fully understands what is being asked. For example, rather than saying "sort array," say "sort a list of integers in ascending order using Python."” — https://github.com/sourcegraph/amp-examples-and-guides/blob/main/guides/context-management/Context%20Engineering%20-%20Amp.md

### B-2. 완료 조건 (26개)

- [explicit] Always include a check the agent can run itself (tests, build, linter, diff script, screenshot comparison); without it the human becomes the verification loop. — “Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from.” — https://code.claude.com/docs/en/best-practices
- [explicit] Put concrete verification criteria (example inputs and expected outputs) in the prompt and tell the agent to run them after implementing. — “write a validateEmail function. example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing” — https://code.claude.com/docs/en/best-practices
- [explicit] Write the done condition as one measurable end state plus a stated check plus the constraints that must not change; phrase it so the agent's own output can demonstrate it. — “One measurable end state: a test result, a build exit code, a file count, an empty queue * A stated check: how Claude should prove it, such as "`npm test` exits 0" or "`git status` is clean" * Constraints that matter: anything that must not change on the way there, such as "no other test file is modified"” — https://code.claude.com/docs/en/goal
- [explicit] Because the completion evaluator only sees the transcript, the done criterion must be something the agent surfaces (test output, exit code), not something checked out-of-band. — “The evaluator judges your condition against what Claude has surfaced in the conversation. It doesn't run commands or read files independently, so write the condition as something Claude's own output can demonstrate.” — https://code.claude.com/docs/en/goal
- [explicit] For unattended/autonomous runs, state explicitly what success looks like and what to do with the results, since the agent cannot ask clarifying questions. — “When writing prompts for scheduled tasks, be explicit about what success looks like and what to do with results. The task runs autonomously, so it can't ask clarifying questions. For example: "Review open PRs labeled `needs-review`, leave inline comments on any issues, and post a summary in the `#eng-reviews` Slack channel."” — https://code.claude.com/docs/en/common-workflows
- [explicit] A self-contained spec/starter names the files and interfaces involved, states what is out of scope, and ends with an end-to-end verification step; invest in the spec rather than in babysitting the run. — “The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works. Time spent making the spec precise pays off more than time spent watching the implementation.” — https://code.claude.com/docs/en/best-practices
- [explicit] Set clear success criteria, expected output format, and repository context in automation prompts. — “Be specific in your prompts - Include expected output format - Set clear success criteria - Provide context about the repository - Use inline comments for code-specific feedback” — https://github.com/anthropics/claude-code-action/blob/main/docs/solutions.md
- [explicit] Optionally bound an open-ended goal with a turn or time clause so the run cannot loop forever. — “To bound how long a goal runs, include a turn or time clause in the condition, such as `or stop after 20 turns`. Claude reports progress against that clause each turn and the evaluator judges it from the conversation.” — https://code.claude.com/docs/en/goal
- [explicit] ⚠간접 Express definition-of-done as observable conditions that must be true before the task is complete (tests pass, behavior changes, bug no longer reproduces); this is what keeps the agent scoped. — “Done when: What should be true before the task is complete, such as tests passing, behavior changing, or a bug no longer reproducing? This helps Codex stay scoped, make fewer assumptions, and produce work that's easier to review.” — https://developers.openai.com/codex/learn/best-practices
- [explicit] ⚠간접 For long-running/autonomous work (Goal mode), write the goal so the agent can verify its own progress: Outcome, Constraints, Verification. — “Write a goal that lets ChatGPT verify its own progress. Include three things when they apply: Outcome: Describe the result you want, not only the activity ChatGPT should perform. Constraints: Name required tools, boundaries, compatibility needs, or approaches to avoid. Verification: Add tests, measurements, or review criteria that prove the work is complete.” — https://learn.chatgpt.com/docs/long-running-work
- [explicit] ⚠간접 The task text doubles as the completion criteria, so a multi-step task must carry outcome, constraints and definition of done in the prompt itself. — “For work that may take many steps, give ChatGPT a clear outcome, constraints, and definition of done. Keep related work in the same chat so ChatGPT can use the same context to choose the next step and decide when the work is complete.” — https://learn.chatgpt.com/docs/long-running-work
- [explicit] Ask the agent to define an output contract up front — exact deliverables (files changed, expected outputs, CLI/API behavior, tests passing) — and to resolve ambiguity from repo conventions. — “Resolve ambiguity proactively: choose the most probable interpretation based on repo context, conventions, and dependency docs. Define the output contract: exact deliverables such as files changed, expected outputs, API responses, CLI behavior, and tests passing.” — https://cookbook.openai.com/examples/gpt-5/gpt-5_prompting_guide
- [explicit] Persistence wording for multi-part tasks: decompose into sub-requests, confirm each is complete, do not stop after a partial result. — “Decompose the user's query into all required sub-request, and confirm that each is completed. Do not stop after completing only part of the request. Only terminate your turn when you are sure that the problem is solved.” — https://cookbook.openai.com/examples/gpt-5/gpt-5_prompting_guide
- [explicit] Phrase acceptance as externally verifiable behavior with concrete inputs/outputs, not as internal code attributes. — “Acceptance should be phrased as behavior a human can verify ("after starting the server, navigating to http://localhost:8080/health returns HTTP 200 with body OK") rather than internal attributes ("added a HealthCheck struct").” — https://cookbook.openai.com/articles/codex_exec_plans
- [explicit] Each milestone must be independently verifiable and incrementally advance the overall goal. — “Each milestone must be independently verifiable and incrementally implement the overall goal of the execution plan.” — https://cookbook.openai.com/articles/codex_exec_plans
- [explicit] Include complete acceptance criteria that say what a good solution looks like, explicitly answering questions like whether unit tests are expected. — “Complete acceptance criteria on what a good solution looks like (for example, should there be unit tests?).” — https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results
- [explicit] ⚠간접 Define success as explicit pass/fail conditions such as 'CI green', 'all existing tests pass', or 'matches the style of ComponentX'. — “Define success criteria like "CI green," "all existing tests pass," or "matches the style of ComponentX" — explicit pass/fail conditions keep you on track.” — https://docs.devin.ai/essential-guidelines/instructing-devin-effectively
- [explicit] ⚠간접 Before generating, check three things: can success criteria be described, is there enough context (files/patterns/docs), and would splitting help. — “Can I describe clear success criteria? Tasks with test suites, CI checks, or verifiable outcomes yield the best results. Is there enough context? Provide relevant files, patterns, docs, or examples. The more context, the better. Would breaking this down help? For very large projects, split the work into focused sessions that build on each other.” — https://docs.devin.ai/essential-guidelines/when-to-use-devin
- [explicit] Give the agent a clear specification or a measurable target it can verify itself. — “Jules excels when you give it clear specifications or measurable targets it can verify.” — https://github.com/google-labs-code/jules-action
- [explicit] ⚠간접 Judge whether a task/issue is well-specified on a graded severity scale (not a binary pass/fail) — mild ambiguity is tolerated, but ambiguity severe enough that a reasonable engineer could not know what 'done' means gets the task discarded/rejected as untestable. — “Each annotation criterion has a label ranging [0, 1, 2, 3] in increasing severity, with labels 0 and 1 being minor, and labels 2 and 3 being severe and indicating that the sample is inadequate in some way and should be discarded.” — https://openai.com/index/introducing-swe-bench-verified/
- [explicit] ⚠간접 Underspecified problem statements are not a rare edge case in real-world GitHub issues — expect roughly a third of raw issue text to be too ambiguous to grade a solution against unless it is actively tightened before handing it to an agent. — “38.3% of samples were flagged for underspecified problem statements, and 61.1% were flagged for unit tests that may unfairly mark valid solutions as incorrect” — https://openai.com/index/introducing-swe-bench-verified/
- [contested] ⚠간접 Tightening issue clarity and fixing unfair acceptance tests together roughly doubled the measured agent solve rate on the same underlying task pool — spec/test quality is a first-order lever on whether an agent 'succeeds,' independent of model capability (see disagreements: this combines two fixes, not clarity alone). — “GPT-4o's performance on SWE-bench Verified reached 33.2%, more than doubling its 16% score on original SWE-bench” — https://openai.com/index/introducing-swe-bench-verified/

## 부록 C. 출처끼리 어긋나는 점

- (Anthropic / Claude Code) Verification instructions: Claude Code best-practices says to always give the agent a runnable check and ask it to run it, iterate, and show evidence ('Give Claude a check it can run... If you can't verify it, don't ship it'), whereas the Opus 5 prompting guide says explicit verification instructions ('include a final verification step', 'use a subagent to verify') and re-check boilerplate ('double-check your answer') cause over-verification and should be removed. Reconciliation suggested by the two texts: specify the concrete check that defines done (test command, exit code, screenshot) rather than generic 'verify/double-check' language, and don't mandate a separate verification pass on Opus 5.
- (Anthropic / Claude Code) Reviewer scoping: best-practices says 'Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional', while the Opus 5 guide warns that 'only report high-severity issues' or 'be conservative' is followed literally and under-reports, recommending 'ask it to report everything and filter in a separate pass'.
- (Anthropic / Claude Code) Prompt precision vs. iteration: how-claude-code-works says 'You don't need perfect prompts. Start with what you want, then refine', but best-practices says 'A clean session with a better prompt almost always outperforms a long session with accumulated corrections' and 'Time spent making the spec precise pays off more than time spent watching the implementation'. For a starter-prompt generator targeting autonomous/cloud runs, the second position applies; the first applies to interactive pair-programming.
- (Anthropic / Claude Code) Clarifying questions: best-practices actively invites questions at spec time (interview with AskUserQuestion; 'Claude asks about things you might not have considered'), while the Fable 5.1 autonomous block says asking 'Shall I…?' mid-task 'will block the work' and auto mode 'nudges Claude to keep working without stopping for clarifying questions'. The docs resolve this by phase: interview before execution, autonomy during execution, and 'Claude still asks when your prompt or a skill explicitly relies on it'.
- (Anthropic / Claude Code) Subagent use: best-practices recommends 'use subagents to investigate X' and a verification subagent, while the consolidated prompting guide notes Opus 4.6 'has a strong predilection for subagents and may spawn them in situations where a simpler, direct approach would suffice', and the Opus 5 guide says 'do not use subagents to verify or double-check your own work'. Model-dependent; a starter should state when delegation is warranted rather than blanket-encourage it.
- (Anthropic / Claude Code) Parallel tool calling: the consolidated page offers a long <use_parallel_tool_calls> system-prompt block, while the Fable 5.1 page says a one-sentence nudge appended per turn ('First privately list what you need next; then request every item that doesn't depend on another's result in this one response.') is the right shape for that model.
- (OpenAI / Codex) Preambles/upfront plans: the GPT-5 general guide recommends prompting for tool preambles and (at minimal reasoning) explicit prompted planning ('Prompted planning is likewise more important'), and GPT-5.1 offers a <user_updates_spec>; the Codex guides say the opposite for Codex models — 'remove all prompting for the model to communicate an upfront plan, preambles, or other status updates … as this can cause the model to stop abruptly' and 'GPT-5-Codex does not emit preambles! Prompting and asking for it will likely result in the model stopping early' (re-enabled only for gpt-5.3-codex via the `phase` field). Rule for a generator: target-model-specific — never ask Codex for progress narration.
- (OpenAI / Codex) Ask-vs-proceed: GPT-5 <persistence> says 'Do not ask the human to confirm or clarify assumptions' and Codex's starter prompt says 'do not end your turn with clarifications unless truly blocked', while the Codex product docs recommend Boundaries that name what to 'check with you before it acts', Plan mode to 'ask clarifying questions', 'Require your approval before ChatGPT sends, publishes, or changes information other people rely on', and the Codex CLI prompt hard-codes 'STOP IMMEDIATELY and ask the user' on unexpected worktree changes and approval requests for destructive actions. The GPT-5 guide itself resolves this: state stop conditions and per-action thresholds explicitly — the sources agree only that the prompt must pick one policy and make precedence unambiguous.
- (OpenAI / Codex) How minimal: the original GPT-5-Codex guide says the Codex CLI prompt 'uses about 40% as many tokens' and 'prompt tuning will more often mean removing guidance than adding it', whereas the current Codex Prompting Guide ships a considerably longer starter prompt (Autonomy, Code Implementation, Exploration, Plan closure sections) and says to 'make tactical additions from there'. Both agree the additions should be about autonomy/persistence, exploration, tool use, and verification — not narration.
- (OpenAI / Codex) Running tests proactively: the GPT-5 SWE-bench instruction says 'You can make as many tool calls as you like … Make sure you are 100% certain', the Codex AGENTS.md sample says 'Fix any test or type errors until the whole suite is green', but the Codex CLI GPT-5 prompt says in interactive approval modes to 'hold off on running tests or lint commands until the user is ready' and the GPT-5 guide's low-eagerness variant caps at 'an absolute maximum of 2 tool calls'. The behavior depends on mode, so a task prompt must say explicitly whether/which checks to run.
- (OpenAI / Codex) Adding tests: Codex CLI prompt — 'do not add tests to codebases with no tests' and 'Do not add inline comments'; agents.md sample AGENTS.md — 'Add or update tests for the code you change, even if nobody asked.' Repo-level AGENTS.md is the intended override channel (the CLI prompt notes 'user instructions (i.e. AGENTS.md) may override these guidelines').
- (OpenAI / Codex) Prose vs structure: PLANS.md says 'Write in plain prose. Prefer sentences over lists. Avoid checklists, tables, and long enumerations', while the Codex Best practices/Prompting docs present bulleted Goal/Context/Constraints/Done-when structures and Cursor found 'structured XML specs … improved instruction adherence'. Likely reconciliation: bullets for short task prompts, prose for long self-contained specs.
- (OpenAI / Codex) Plan-first vs code-first: Codex Best practices lists 'Skipping planning on multi-step and complex tasks' as a common mistake and recommends /plan or an interview first, while the Codex starter prompt says 'Unless asked for a plan, never end the interaction with only a plan' and 'Skip using the planning tool for straightforward tasks (roughly the easiest 25%)'. Planning is a separate, explicitly requested mode; a task prompt that wants plan-only must say so.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Specifying files: GitHub lists 'Directions about which files need to be changed' as part of an ideal task and Amp says to put 'which files to look at, which commands to run' in the prompt, but GitHub's own tip says the agent 'can often discover the right code on its own' via semantic search, and Cursor's agent blog (unfetched) favors letting the agent grep/semantic-search and produce a plan with file paths first. Net: file anchors are recommended but optional, not mandatory.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Where repo knowledge lives: GitHub insists repo instructions 'must not be task specific' and be 'broadly applicable' (task detail goes in the prompt/prompt file); Devin splits Playbooks (task procedures) from Knowledge (broad conventions); Aider treats conventions as a per-session read-only file; Gemini/Cursor/Amp use hierarchical or glob-scoped files loaded just-in-time. The file name itself is fragmented (copilot-instructions.md, .instructions.md, .cursor/rules/*.mdc, GEMINI.md, AGENT.md, AGENTS.md, CONVENTIONS.md), though Copilot and Gemini CLI now also read AGENTS.md/CLAUDE.md.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Length limits differ in unit: Cursor 'Keep rules under 500 lines'; GitHub 'no longer than 2 pages' plus 'short, self-contained statements'; Gemini/Amp prefer splitting via imports/@-mentions rather than a hard cap.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Task size: Devin gives a time heuristic ('three hours or less'); Jules examples give diff-size caps ('under 100 lines', 'under 50 lines'); GitHub gives qualitative categories (avoid broad refactors, deep domain, security/PII) with no numeric bound.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Style/persona in always-on files: GitHub warns 'Instructions to answer in a particular style' and fixed detail levels 'may cause problems' in large repos, whereas Gemini CLI docs explicitly say context files can 'define a persona' and Cursor rules commonly include tone guidance.
- (Copilot · Cursor · Devin · Gemini CLI · Jules · Aider · Amp) Clarifying questions: Amp guidance assumes the agent 'relies heavily on the clarity and completeness of your input' (no clarifying questions), while Cursor's blog and Jules' plan-approval flow encourage prompting the agent to ask questions / propose a plan before coding; GitHub's onboarding prompt tells the agent to 'trust the instructions and only perform a search if ... incomplete'.
- (연구·스펙 주도 개발(SWE-bench Verified, Kiro, spec-kit)) The widely-cited '16% → 33.2%' SWE-bench Verified solve-rate jump for GPT-4o comes from removing underspecified issues AND unfair/overly-strict unit tests together in one filtering pass; OpenAI's post does not isolate how much of the gain is attributable to issue-description clarity alone versus test-fairness fixes, so treating it as clean evidence that 'clearer issue text raises solve rate' overstates what was actually measured.
- (연구·스펙 주도 개발(SWE-bench Verified, Kiro, spec-kit)) The clarification-seeking literature (Ask or Assume?, Asking What Matters) evaluates agents that can interactively query a simulated user mid-task and shows gains from asking a few well-targeted follow-up questions (e.g. +8.2pp resolve rate; matching a larger model's resolution rate with 41% fewer questions). That is a different paradigm from a single, non-interactive starter prompt handed to a coding agent with no back-channel — it argues for 'build in a lightweight clarify-first step' more than for 'the upfront prompt must anticipate and answer everything,' and the two prescriptions are complementary rather than interchangeable for a prompt-generation tool that produces one-shot starters.
- (질문 시점 연구·벤더 지침) OpenAI's two flagship prompting guides (GPT-5 and Codex) both default to proceeding on reasonable, documented assumptions and treat a clarifying question as a last resort ('truly blocked'), while Anthropic's Claude Code product design (interview mode, AskUserQuestion's 'genuinely the user's to make' criterion, plan mode) and the reviewed academic literature (ClarifyGPT, AwN, ClarifyCoder) treat asking before generating as the change that improves quality. Both vendors present this as a tunable dial via prompt language rather than a fixed rule, so the disagreement is about the recommended default, not about whether asking is ever appropriate.
- (질문 시점 연구·벤더 지침) Within Anthropic's own prompting-best-practices page, two officially provided example system-prompt blocks (<default_to_action> vs <do_not_act_before_instructions>) instruct opposite defaults for the identical situation — ambiguous user intent — and the doc explicitly leaves the choice to the prompt author. There is no single Anthropic-recommended default; only a documented dial, mirroring the OpenAI-vs-Anthropic split above but internal to one vendor.
- (질문 시점 연구·벤더 지침) Reported product behavior suggests consumer/'vibe-coding' tools (per third-party comparisons of Lovable) favor fast, immediate execution on a vague prompt over up-front clarification, while professional-facing agentic tools (Cursor Plan Mode, Replit Plan Mode, Claude Code plan mode, Codex Plan mode) converge on asking or planning before code changes. Lovable's own reachable docs do however explicitly recommend Plan Mode for 'multi-file or ambiguous changes,' so this may be a matter of default UX rather than a stated policy difference.
- (질문 시점 연구·벤더 지침) The reversibility/blast-radius criterion (Anthropic: ask before destructive, hard-to-reverse, or shared-visibility actions) and the per-tool-threshold criterion (OpenAI's GPT-5 guide: e.g., delete-file tool needs a much lower confirmation threshold than a grep tool) express the same underlying idea at different granularities — one gates by action category, the other by which specific tool is about to run — and neither source cites the other, so it is unclear whether this is convergent design or one borrowing from the other.
