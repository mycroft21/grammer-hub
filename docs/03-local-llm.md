# 로컬 LLM 판정: Mac 32GB에서 서비스가 되는가 (v0.1, 2026-09-15)

> 질문: Gemma 같은 로컬 모델로 가능한가? 너무 느려서 의미가 없나? Mac 32GB면 어느 정도 결과물이 나오나?
> 근거: 리서치 원문은 [`00-references.md` F절](./00-references.md). 지연 수치는 `tools/latency_local.py`(llama.cpp Apple Silicon 실측을 앵커로 스케일한 추정치).

---

## 0. 결론 먼저

| 질문 | 판정 |
|---|---|
| 32GB Mac에서 되는가 | **된다. 단 모델을 골라야 한다.** Gemma 4 26B-A4B(MoE, 4비트 15GB)면 M4 Pro에서 300자 보고 교정이 **5~10초**. Gemma 4 31B 같은 dense 30B급은 **30~60초**라 전송 직전 교정에는 못 쓴다. |
| 너무 느려서 의미 없나 | **MoE를 쓰면 의미 있다.** 고정 프롬프트 2,500토큰을 KV 캐시로 상주시키는 것이 전제. 이걸 안 하면 매 요청 15~25초가 추가된다. |
| 결과물 품질 | **한국어 문체는 Gemma 4가 오픈 모델 중 최상급.** 지식 벤치마크는 프론티어 대비 5~10점 뒤진다. 어투 교정 품질은 우리 데이터로 실측해야 하며, 맞춤법(L1)은 오히려 소형 파인튜닝 모델이 GPT-4o를 이긴다. |
| 로컬로 가는 진짜 이유 | 비용 절감이 아니다. 개인용 클라우드 비용은 월 ₩9,000이라 로컬이 아끼는 돈이 작다. 이유는 **① 사내 데이터 외부 전송 회피, ② API 종속 제거, ③ "내 Mac에서만 도는 한국어 교정기"라는 비어 있는 제품 포지션**이다. |
| 권장 | 백엔드를 처음부터 **교체 가능하게**(클라우드 Sonnet 5 / 로컬 llama-server, 동일 JSON 스키마) 만들고, 첫 주에 내 메시지로 두 경로를 나란히 실측한다. |

## 2. 속도: 칩 × 모델 × 우리 워크로드

가정: 고정 프롬프트 2,500토큰은 llama-server slot 캐시로 상주(재계산 없음). 동적 부분은 예시·프로필·개인 사전 900토큰 + 초안. 한글 1자 ≈ 1토큰. 출력은 L2가 edits JSON만 내면 250토큰, 교정문까지 포함하면 550토큰, L3 리라이트 3안은 1,400토큰.

읽는 법:
- **M5 기본형 32GB(사용자 확인된 기기) + Gemma 4 26B-A4B**: L2 edits만 7초, 교정문 포함 16초, L3 3안 39초. 대역폭 153GB/s가 디코드를 제한하므로 **출력 토큰을 줄이는 설계(edits만 반환, 교정문은 서버에서 합성, L3는 1안)**가 필수. dense 30B급은 45초 이상으로 제외.
- **M4 Pro 32GB + Gemma 4 26B-A4B**: L2 5~10초, L3 3안 23초. 전송 직전 교정으로 쓸 만하다. L3는 1안씩 스트리밍하거나 기본 1안만 생성해야 한다.
- **M4 Pro + dense 30B급**: 30~60초. 인터랙티브 불가. 밤에 돌리는 "지난주 메시지 일괄 재교정"이나 주간 어투 증류에는 쓸 수 있다.
- **M2 Pro 32GB**(구형)라면 MoE도 8~14초로 빠듯하고, dense는 1분 이상.
- **M5 Pro/Max**면 prefill 병목이 풀려 12B dense까지 인터랙티브 범위에 들어온다.
- 콜드 스타트(캐시 미적중) 열을 보면 캐시 상주가 왜 필수인지 드러난다. dense 31B는 캐시 없이는 매번 1분이다.
- 실측 보정: M5 Max에서 Gemma 4 31B를 Ollama로 돌린 보고는 디코드 15 tok/s(플래시 어텐션 꺼짐)로 위 표(24)보다 느렸다. 표는 최적 설정 기준이라 실사용은 20~30% 느릴 수 있다.

## 3. 품질 격차 근거

- **맞춤법(L1)은 소형 파인튜닝 모델이 프론티어를 이긴다.** KoGEC(NLLB 3.3B 파인튜닝) BLEU 85.7 대 GPT-4o 75.0 대 HyperCLOVA X 71.2. 600M은 58.2로 부족해 "3.3B 이상" 결론. 단 소셜 대화체 데이터라 비즈니스 문체는 별도 검증 필요.
- **지식·추론 벤치마크(KMMLU-Redux)**는 프론티어 78~80 대 오픈 30B급 67~75로 5~10점 격차.
- **어투·톤 교정** 자체를 비교한 공개 벤치마크는 없다. 커뮤니티 실무 테스트에서 Gemma 4 31B가 Claude Sonnet 4.6 대비 "쓸 만하다"는 정성 평가 정도.
- Apple 온디바이스 3B(Foundation Models)는 한국어를 지원하고 구조화 출력도 되지만, Writing Tools 한국어 평이 "아직 어색"이라 오탈자 1차 패스 이상은 어렵다. 다만 macOS 27부터 같은 프레임워크에 MLX 모델을 꽂을 수 있게 된 점은 제품 구조상 유리하다.

시사점: **로컬 L1(KoGEC 3.3B 또는 규칙층) + 로컬 L2(Gemma 4 26B-A4B) + 선택적 클라우드 L3**의 3단 구성이 격차를 실용적으로 줄인다.

## 4. 로컬 구현 스택

| 구성 | 선택 | 이유 |
|---|---|---|
| 추론 서버 | **llama-server** (llama.cpp) | `--cache-reuse` + `--slot-save-path`로 2,500토큰 prefix를 디스크 보존·복원. `json_schema`/GBNF로 출력 강제 네이티브 지원. Gemma 계열은 `--swa-full` 필요 |
| 대안 | mlx_lm / LM Studio | 14B 이하에서 20~87% 빠르나 캐시 영속화 PR이 미머지 종료, 서버가 `response_format`을 무시해 Outlines를 직접 붙여야 함 |
| 모델 파일 | Gemma 4 26B-A4B QAT Q4_0 (15GB) | Ollama 공식 라이브러리에 있으나 Ollama의 MLX 백엔드는 Gemma 4 미지원(GGUF 폴백) |
| L1 전용 | KoGEC NLLB 3.3B | 라이선스(NLLB 계열 CC-BY-NC 가능성) 확인 후 개인용 우선 |
| 앱 형태 | 전역 단축키 유틸(Raycast/Electron 트레이) → 로컬 llama-server | 클라우드 백엔드와 같은 `/correct` 계약 |

메모리 예산(32GB): 모델 15GB + KV 캐시(4K 컨텍스트) 1~2GB + OS·브라우저·메신저 8~10GB. 여유가 있다. 31B dense(18.7GB)도 들어가지만 다른 앱과 함께 쓰면 스왑 위험.

## 5. 개인용 vs 로컬 퍼스트 제품

### 5.1 개인용
- 가능하고 실용적. 비용 0, 데이터 외부 전송 0.
- 대가: 응답 5~10초(클라우드 2~4초), L3 대안은 1안씩. 품질은 실측 전까지 미지수.
- 클라우드 대비 절감액은 월 ₩9,000. **절감이 목적이면 의미가 작고, 데이터 통제가 목적이면 의미가 크다.**

### 5.2 로컬 퍼스트 제품
- 경쟁 공백: 한국어 특화 로컬 교정기는 발견되지 않았다. 영어권 유사 제품은 Grambo $19.99 평생, Private LLM $9.99, EmberType $39 등 **일회성 $10~40**.
- 장벽: 32GB 이상 Mac 필요(16GB는 12B 폴백), 15GB 다운로드, 상업 가능 모델이 Gemma 4·Qwen·Mi:dm으로 한정.
- 원가 구조는 클라우드 제품과 정반대다. 추론 원가 0, 대신 개발·지원 비용만. ₩9,900/월 구독의 30~50% 마진 문제에서 자유롭다.
- 현실적 형태: **일회성 ₩30,000~50,000 + 선택형 클라우드 티어(Sonnet 5로 L3·고품질 모드, 월 ₩5,000)**.

### 5.3 타이밍
"너무 늦었나"에 대해: 로컬 모델의 한국어 품질이 실용 구간에 들어온 것이 2026년 상반기(Gemma 4)이고, 한국어 특화 로컬 교정기는 아직 없다. 늦지 않았다. 다만 카카오워크·뤼튼 같은 무료 번들과 경쟁하려면 "내 데이터가 회사 밖으로 안 나간다 + 내 어투를 학습한다" 두 가지가 명확해야 한다.
